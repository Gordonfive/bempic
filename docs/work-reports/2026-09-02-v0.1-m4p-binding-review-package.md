## Exact binding contract

The profile is `bempic-m4p-opaque-record-v0.1-review`, revision 1.

Outbound `submit_record` takes:

- `record_bytes`: one complete canonical encoded BEMPIC operation, mapped to
  the M4P application payload;
- `destination_client_uid`: supplied by the application-authorized endpoint
  binding;
- `binding_message_type_id`: deployment configuration, not a BEMPIC field and
  intentionally unallocated pending review; and
- `local_submission_ref`: local-only correlation, never encoded or forwarded.

The normalized status is exactly `accepted`,
`not-accepted-record-too-large`, `not-accepted-invalid-destination`,
`not-accepted-binding-unconfigured`, `not-accepted-backpressure`,
`not-accepted-local-error`, or `acceptance-unknown`. `accepted` does not mean
send, persistence across restart, peer delivery, destination application
delivery, or BEMPIC receipt.

Inbound `receive_record` returns only `record_bytes`, resolved-or-null
`source_client_uid`, `source_resolution`, and local-only `local_delivery_ref`.
The binding rejects or quarantines unresolved/unauthorized sources outside
BEMPIC state and emits no BEMPIC receipt from them.

The current M4P application boundary exposes no prescribed opportunity or
carrier/physical cost. Those counters remain unavailable unless an externally
confirmed implementation contract defines them. The package records BEMPIC's
1,048,576-octet outer operation ceiling and M4P's 65,535-octet per-packet
payload-length ceiling, but leaves the safe complete M4P application-record
maximum null because the 15-bit fragment offset and 16-bit fragment payload
length do not establish an explicit source-defined maximum.

## Layer and repository-boundary decisions

- OceanMail/application owns application object semantics, authorized-source
  sets, deployment Message Type catalog, and product policy.
- BEMPIC owns operation bytes, selection, durable representation prefix,
  integrity, application idempotency, semantic receipts, and BEMPIC budgets.
- M4P owns `ClientUID` resolution to mission-scoped addresses, network routing,
  forwarding, mesh coordination, store-carry-forward, network TTL,
  retained-record resend/spacing, fragmentation/reassembly/Fragment NACK, MIID
  deduplication, M4P Packet/Transmission accounting, and cross-modality
  scheduling.
- DataLink/modem owns link framing, FEC, ARQ, frame retransmission, and physical
  byte accounting.
- M4P deliberately omits custody transfer. M4P store state is not a BEMPIC
  commit, receipt, or custody promise.
- A BEMPIC retry is a fresh M4P Message instance carrying the identical complete
  BEMPIC operation. M4P network-copy suppression and BEMPIC application
  idempotency remain distinct.
- Only specification, conformance, validators, and documentation changed in
  this repository. No implementation work was added here or to any sibling.
