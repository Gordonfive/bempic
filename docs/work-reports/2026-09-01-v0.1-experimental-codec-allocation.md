## Assignment scope and outcome

This change audited the compact operation-codec candidate at immutable
`Gordonfive/bempic-reference@cf3485f6606d6462077e8edd1592264c3ce4ca5e`
and the application-owned object-identity evidence at immutable
`Gordonfive/oceanmail@cc55c1b7d5a03aa2e5cc8cd617f9d1bb7b6a3600`.
Both sibling repositories were read only.

The Reference evidence contains every item required for a provisional
experimental allocation: a public candidate profile; canonical empty
parameters; complete field, collection, nesting, and resource bounds; exact
size formulas; finite maxima and seven reaching witnesses; valid,
invalid/boundary, malformed, one-past, and context-failure draft vectors;
50,000 general malformed cases, 175 structured malformed cases, and 4,100
exact-size property cases with zero reported unresolved finding; a distinct
Python decoder/verifier; Apache-2.0 licensing; explicit public-cleartext
security limitations; and measured 35 B warm / 75 B cold V01 operations.
The prior registry was empty and `0x00010000` was the first collision-free ID in
the experimental range, so revision 1 was allocated.

This decision satisfies the experimental allocation minimum only. It does not
approve or mandate the codec and carries no stable-wire or production-security
promise. The source candidate remains private tuple `0xffff0001/2`.
Implementations use public tuple `0x00010000/1`; the ID change alters tuple-bound
operations and representation IDs, and consequently descriptors, collection
digests, vectors, and bundle digests. The private candidate's bytes and digests
therefore remain allocation provenance and must be regenerated before they can
be public-tuple conformance or release evidence.
