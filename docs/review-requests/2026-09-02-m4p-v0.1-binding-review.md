# Draft: request for M4P review of the BEMPIC v0.1 opaque-record binding

**Do not post or send without explicit authorization.**

Hello M4P maintainers,

BEMPIC is preparing a v0.1 application-layer conformance package and would
value your review of its proposed M4P boundary. We have based the package on
`m4p-spec@2eca9e8f57d43dab250cc26c1bbf2d255e3331de` and attributed the
CC-BY-4.0 specification. We have not copied or linked M4P or AGPL code and are
not asking you to approve BEMPIC itself.

Our proposal submits one complete canonical BEMPIC operation as an opaque M4P
application Message payload addressed by `ClientUID`. BEMPIC retains
application selection, durable prefix resume, integrity, idempotency, and
semantic receipts. M4P retains addressing, routing, forwarding,
store-carry-forward, TTL, fragmentation/reassembly, MIID deduplication,
retained-record resend scheduling, cross-modality behavior, and its DataLink
boundary. DataLink/modem ARQ and frame retransmission stay below M4P. No M4P
send, peer-holding, or delivery indication is treated as a BEMPIC receipt, and
we understand that M4P does not provide custody transfer.

Could you please confirm or correct that boundary and answer the eight numbered
questions in `docs/M4P-CONFIRMATION.md`, especially:

- the safe maximum complete application payload;
- the suitable deployment-owned directed Message Type / Request-Response
  mapping for independent bidirectional BEMPIC operations;
- the implementation API mapping, accepted-message restart persistence, and
  cancellation/backpressure/expiry/cost signals;
- address scope or federation, mixed-version, long-lived delivery, and
  unresolved-source behavior; and
- whether the prescribed V09, V10, and V12 traces correctly distinguish M4P
  network behavior from BEMPIC application behavior.

The complete machine-readable proposed interface, source identities, trace
steps, pass criteria, and open questions are in
`conformance/v0.1/m4p-binding-review-package.json`. We will keep the BEMPIC M4P
release gate blocked until an authorized M4P reviewer provides an immutable
affirmative review and the implementation traces pass. Corrections are welcome;
we will reconcile them through BEMPIC governance rather than infer approval.

Thank you for helping us keep the layer boundary precise and interoperable.
